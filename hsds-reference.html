ARCHITECTURE AT A GLANCE
LAYER 0 The Vault — Sealed Core §1.2 ▼

Static Rust binary. WireGuard mesh. Ed25519 identity. Memory-mapped binary state (system.bin). Read-only after SEAL. Fail-closed on any integrity violation. Binary size ≤ 1.1MB ARMv6, ≤ 2MB all targets.

Layer 0 is the only trusted execution boundary. Services cannot read /config/keys/, cannot write /config/, cannot touch /system/. Layer 0 failure is system failure. Layer 1 failure is isolated.

LAYER 1 Service Layer — Daily Computing §11 ▼

Modular isolated processes. Installed via service_install in LANDING only. Each service has a 400-byte manifest.bin, a single declared WireGuard-internal port, and sandboxed data at /data/services/<id>/.

Maximum 8 services. Service binary frozen after SEAL alongside core. A failing service does not affect Layer 0. Services run under node role — no escalation.

TECH Technology Stack §5, §11 ▼

Core persistence: binary_layout — zero-copy, little-endian, compile-time offsets, memory-mapped. No heap allocation during read/write.

Service config: binrw — declarative parsing for dynamic service data. Not used in Layer 0.

Scripting runtime: QuickJS via quickjs-rs (~2MB). Reference-counting GC, <300µs startup. AArch64 + x86_64 only. ARMv6 rejected at APPLY.

OS: Alpine Linux diskless — full system in RAM, lbu for persistence overlay. musl static linking, zero runtime dependencies.

CONSTITUTION §3
Lifecycle State Machine FROZEN
Six states. Unidirectional except for recovery paths. ROLLBACK is a binary atomic switch originating from SEAL only — v1 is authoritative on this point.
GENESIS Identity creation, initial config §3.1 ▼

Ed25519 identity key generated locally. WireGuard X25519 keypair created. system.json written (v1) or system.bin initialized (v2). No services installed. Legacy JSON import accepted here only.

GENESIS is the only state where new identity can be created. After GENESIS, identity is immutable until Re-Genesis (which destroys it).

LANDING Mutable staging environment §3.2 ▼

The only state where services may be installed or removed. WireGuard keys are rotatable in LANDING. Configuration is mutable. This is the pre-production holding state before APPLY convergence.

Key rotation in LANDING follows fleet consensus: old key remains active until all nodes acknowledge the new key. Non-acknowledging nodes are marked unreachable and must re-pair. REF: §9.2 (v1 §8.2/§8.4 carried forward)

APPLY Atomic convergence of intent → reality §3.3 ▼

Atomic convergence step. Service manifests validated. Fleet ceiling (32 nodes) enforced. Service ceiling (8 services) enforced. ARMv6 nodes reject sealed_js services here. State transitions to binary format after APPLY — JSON no longer authoritative.

SEAL Immutable, production, locked §3.4 ▼

/system/ and /config/ become read-only. Service binaries frozen alongside core. No configuration changes permitted. Cockpit is observation-only. This is the normal operating state.

SEAL is the only valid origin state for ROLLBACK.

ROLLBACK Atomic binary switch, no state change §3.5 ▼

Reverts the active binary to the previous known-good version. State is not modified. Service state preserved across rollback. This is a pure binary swap — integrity guarantees rest on build artifacts.

Origin: SEAL only. v1 is authoritative. ROLLBACK reverts a deployed binary; a binary is only deployed after SEAL. REF: C-04 resolved 2026-06-07

REBUILD Full reinstall of /system §3.6 ▼

Full reinstall of /system. Optional restore of /config, /data/storage, and /data/services from backup. Services re-installed from manifests during LANDING after REBUILD. Re-Genesis is the nuclear option: destroys identity, removes all services, creates new identity.

§5.1 Persistence format — binary_layout ▼

Location: /config/system.bin. Encoding: binary_layout, little-endian. All field offsets computed at compile time via const generics. Memory-mapped — state updates write directly to mapped memory, OS handles persistence. No JSON after APPLY.

Legacy /config/system.json accepted for import during GENESIS only. After APPLY, binary format is the sole authoritative representation.

§5.5 Integrity check at startup ▼

SHA-256 of system.bin verified at every startup. Mismatch → fail-closed (exit(1)). This is the first operation in main.rs, before any other initialization. A compromised state file will never silently execute.

§9.2 WireGuard key rotation consensus (v1 rule carried forward) ▼

Old key remains active until all fleet nodes acknowledge the new key. Non-acknowledging nodes are marked unreachable and must re-pair. Grace period must not be removed. This prevents a split-fleet scenario where some nodes still present the old key.

v2 adds: auto endpoint negotiation initiated by the node with the lower identity fingerprint. Deterministic tie-breaking prevents race conditions on first handshake. REF: S-04 resolved 2026-06-07 — v1 §8.2/§8.4 explicitly carried forward

§9.5 Service identity (v2 new) ▼

Services have no independent identity. A service inherits the node fingerprint of its host. Services cannot present themselves as independent fleet members. The node is the trust boundary; services are subordinate.

§10.3 Lockdown behavior ▼

Drops all WireGuard tunnels AND all service ports. Complete node isolation. v2 extends v1 lockdown to cover service ports — v1 dropped tunnels only. No exceptions.

§10.4 Service network rules (v2 new) ▼

Each service may bind exactly one declared port within the WireGuard interface. Services may not open external sockets. Port declarations are immutable after SEAL. The single-port constraint enforces minimal attack surface per service.

§7 Permissions model — roles ▼

Four roles: admin · operator · node · guest. Role set is frozen — no dynamic roles, no wildcard permissions. Services run under node role and cannot escalate. Service actions require operator or higher.

CONSTITUTION §11
Service Layer Contract v2 NEW FROZEN
Self-contained isolated processes on top of Layer 0. No access to identity keys, core config, or WireGuard private key. A failing service does not affect Layer 0.
§11.3 Isolation rules ▼

Services may not read /config/keys/. Services may not read or write /system/. Services may not write /config/. Services may not spawn child processes outside their own directory. Services may not execute dynamic code — except sealed_js services under §11.7 (explicit carve-out).

§11.4 Service lifecycle ▼

Install: LANDING only, via service_install. Remove: LANDING only, via service_remove. Start/stop: managed by hsds-core, event-emitted, not a separate API action. After SEAL: service binary and config are read-only.

Services do not restart automatically without explicit re-seal. A crashed service requires ROLLBACK → LANDING → APPLY → SEAL to restart. This is intentional — automatic restarts would allow a service to influence sealed state.

§11.5 Configuration format ▼

Service configuration files use binrw-compatible binary formats. No JSON in service configuration. Config is bundled in the service archive alongside manifest.bin at install time.

binrw handles variable-length strings, dynamic lists, and complex binary formats — things binary_layout avoids to maintain zero-copy semantics. Layer 1 trades some performance for maintainability and dynamic data support.

RATIONALE Why QuickJS, not V8 ▼

Footprint: QuickJS produces ~4KB for a hello-world; V8 (Rusty V8) approaches 50MB binary overhead. HSDS binary ceiling is 8MB for sealed_js services — V8 is structurally impossible.

GC: QuickJS uses reference-counting GC. Deterministic, no stop-the-world pauses, compatible with ARMv6 timing constraints (for non-sealed_js services).

Startup: QuickJS runtime initialization < 300µs. Suitable for headless service restarts without visible latency.

ES2023: Full spec coverage including modules, async generators, proxies, BigInt. Sufficient for Layer 1 service logic.

§11.2 Manifest fields for sealed_js ▼

script_type[1] — value 0x01 indicates sealed_js. Carved from reserved[].

script_hash[32] — SHA-256 of the compiled bytecode bundle. Verified at service start. Mismatch → service rejected, event emitted, Layer 0 unaffected.

Both fields fit within the 400-byte manifest: reserved field is [u8; 84] after allocating script_type[1] + script_hash[32]. Byte sum verified: 400. REF: C-05-FLAG resolved 2026-06-07

CONSTITUTION §11–13
Security Contract FROZEN
Fail-closed is not a feature — it is the only response to any violation. No partial trust. No graceful degradation. Halt and alert.
§13.1 Integrity surfaces ▼

Six integrity planes, all monitored: binary integrity (core) · binary integrity (services) · config integrity · directory integrity · WireGuard integrity · state file integrity (SHA-256 of system.bin).

All six must hold. Violation on any plane → isolate, reject, alert. No exceptions.

§13.3 No shell, no root ▼

No interactive execution surfaces at any layer. Services do not run as root. No sudo path. No shell spawning. The attack surface is: one WebSocket endpoint, one HTTP cockpit endpoint, one WireGuard port. Nothing else is listening.

ZERO TRUST Three-way identity match ▼

A node trusts another only if: (1) identity fingerprint matches, (2) WireGuard fingerprint matches, (3) node is listed in system.bin. All three conditions must hold simultaneously. Failure on any single condition = rejection. No partial trust, no fallback.

CONSTITUTION §14
Recovery Contract FROZEN
Four recovery paths. All reversible except Re-Genesis. Every node ships with offline recovery documents readable without tooling.

§14.1 Backup scope (v2 extended) ▼

Atomic snapshots of: /config · /data/storage · /data/services. v2 adds /data/services to backup scope. All snapshots are atomic. SHA-256 manifest per snapshot.

Note: /config includes /config/keys/. Keys are backed up intentionally — needed for recovery. 700 permissions enforced; keys never included in event streams or cockpit output.

§16 Human recovery documents ▼

Every node must include: GJENOPPRETTING.md · HSDSv1Constitution.md · HSDSv2Constitution.md. These documents must be readable offline, without tooling, in plaintext. The system must be recoverable by a human with only these documents and a working machine.
